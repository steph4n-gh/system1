# System 1 1.0.3

This patch fixes the six reported security boundaries around receipts, audit
storage, saved skills and the optional gRPC service. It also includes the numeric
teaching/calibration split fix and supervised Paperclips example from the prior
development commit. The teach, validate, save and run-local workflow needs no
new runtime dependency.

## Security changes

- Receipt authentication requires an independently trusted public key. Unsigned
  diagnostics remain available through `check_decision_receipt_integrity()`.
- A committed ledger record ID is bound in the existing signed envelope. The
  core receipt digest stays stable for execution-outcome linkage. Guards verify
  the exact record instead of trusting a nonempty identifier.
- Every ledger write verifies the whole chain within its transaction, including
  previously checked rows and signatures under the current trust key.
- gRPC requests select a built-in or explicitly registered schema. Dynamic
  imports, file paths, inline JSON and unknown-name fallback are no longer
  available over the network; aliases share a finite cache.
- Saved-skill loading checks compressed and expanded sizes, NPY headers,
  dimensions, covariance/calibration shapes and estimated runtime memory before
  allocation. NumPy pickle loading is explicitly disabled.

## Migration

Pass a trusted key explicitly:

```python
from system1 import check_decision_receipt_integrity, verify_decision_witness_receipt

authentic = verify_decision_witness_receipt(receipt, public_key=trusted_public_key)
consistent = check_decision_receipt_integrity(receipt)  # no signer authentication
```

Use `system1 verify-receipt receipt.json --public-key trusted.pub` for CLI
authentication. Do not obtain that trusted key from the receipt being checked.
`TypeSafeClient.compare()` reports authenticated local receipts only when the
client has a configured signing key.

Register custom gRPC names at startup with `serve(schemas={"support": schema})`.
The trusted local CLI schema loader retains its existing file/import/JSON support.

Old signed receipts without a ledger ID remain verifiable with their trusted key.
Old receipts with an unbound nonempty `ledger_record_id` fail current verification.
Preserve them as historical evidence and check their original ledger, or issue a
fresh decision; do not treat editing old receipt metadata as re-attestation.
The `.s1m` format remains v2, and valid v1/v2 files within the documented budgets
continue to load. See [deployment boundaries and exact limits](../deployment.md).

## Validation

Bounded reproductions were run against scanned commit `896ffc35` and this patch.
The old code accepted a receipt-selected key, accepted a forged ledger ID,
extended a tampered cached ledger prefix, retained three unknown guard names,
triggered a sentinel module import, and reached NumPy with oversized model
metadata. The patched code rejects each trigger; unknown names retain zero
entries. No memory-exhaustion payload was executed.

Regression coverage also checks removed/replaced ledger IDs, borrowed record
IDs, both cached and fresh decisions, every ledger write path, changed trust
keys, schema aliases, ZIP duplicates and expansion limits, forged NPY shapes,
object arrays, and valid saved-skill reloads. Existing teaching, calibration,
observation, game, protobuf, policy and execution tests remain the compatibility
checks. The full local suite passes **1,144 tests**, with 14 optional tests skipped.
Documentation/lock checks, distribution validation and installed-wheel smoke
tests are also required before release.

Full-chain checks grow with ledger history. Applications using durable audit
paths should measure their whole-operation latency; core decision timing alone
does not include durable audit verification. In the first CI run, the 100-request,
four-worker audit test measured 26–49 requests/second across the five runners,
below its former 50 requests/second assertion. That assertion is replaced with
successful completion and full-chain signature verification; measured throughput
remains in the benchmark output. This patch does not establish new classifier
accuracy or adversarial-detection claims.

The release tag is pushed only after CI passes on the exact version commit.
That tag triggers the existing PyPI Trusted Publishing workflow.
